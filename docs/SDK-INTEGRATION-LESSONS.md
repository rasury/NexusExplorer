# 原生第三方 SDK 的默认配置：本次音频问题的警示

记录日期：2026-10-04。适用于本项目使用 LibVLC，以及以后接入 FFmpeg、CefSharp 等封装大型 C/C++ 库的 SDK 时。

**功能强大、接口简单，不意味着底层行为简单。默认配置是一个需要验证的运行方案，不能作为质量和性能保证。**

这类集成需要同时考虑封装层、原生库、插件、平台能力和最终输出。历史兼容、自动选择、格式转换与回退机制都应成为排查候选。对不崩溃、却持续降低质量的现象，成功返回和没有异常提供的保证很有限。

## 本次已经验证的事实

- 相同音频在系统播放器和官方 VLC 正常，在 NexusExplorer 中从头到尾破音；调低音量减轻但未消除。用户后来补充，视频音轨也有破音。
- 前期截获的前十秒解码 PCM 与独立解码器结果接近，未发现削波。但该回调替代了系统输出，未验证真正听到的声音。
- 用户使用 Python 直接加载软件目录内同一份 LibVLC，单独实验参数，确认启用 `--aout=directsound` 后完全正常，并确认与 Music/None 角色无关。
- 正式播放器随后为音频与视频统一选择 DirectSound。两项最小原生测试验证实际选中该模块，且解码、音量、跳转、暂停恢复和停止释放正常。正式应用的实际听感另行验收。

这些证据支持更换音频输出路径。它们还没有定位 MMDevice/WASAPI、格式协商、驱动或其他内部环节中的具体缺陷，也不能证明“为了兼容 Win7/XP 留下的参数”就是本次原因。DirectSound 是本项目当前经过用户对比的方案，不是其他项目和 SDK 的通用答案。

相关证据：[验证记录](VERIFICATION.md)、[可编辑音频实验](../tools/AudioLab/README.md)、[正式播放实现](../src/NexusExplorer/Services/MediaPlayerService.cs)。

## 后续排查顺序

1. **固定复现条件。** 记录同一输入、异常位置与操作，区分固定内容失真、随机抖动、切换后异常和运行时长相关的退化。先比较参考应用，再比较同一原生库的最小宿主。
2. **确认真正运行的配置。** 记录封装与原生版本、库和插件路径、实际选择的模块、输入及输出格式、音量与处理参数。核对返回值和回退；请求某个模块与实际加载它是两件事。
3. **早做底层配置对比。** 每次只改变输出模块、解复用器、硬件路径或转换参数中的一项，重复同一场景。保留用户可编辑的实验方式，减少每次改动都需要整套界面和发布流程的成本。
4. **按链路定位。** 区分输入、解复用、解码、转换或音效、输出模块、最终设备。采集点正常，只能缩小该点之前的问题范围；替换输出的诊断回调会绕过需要验证的部分。
5. **有证据地处理宿主。** 检查线程、生命周期、渲染负担和调用顺序；扩大架构改造前，明确它与现象之间的证据。软件里已有的独立缺陷仍应修复，但不能据此宣布质量问题已解决。
6. **固化经过验证的选择。** 在应用中明确关键参数，覆盖所有共享入口，记录选择理由。最小测试检查实际行为；真实听感、画面和性能结果单独验收。升级封装、原生库或运行环境时重新确认。

## 对其他质量和性能问题的应用

| 现象 | 优先收集与对比 |
|---|---|
| 音质异常、破音、同步偏移 | 真实输出与参考应用；输出模块、采样格式、时钟和处理参数；解码采集是否绕过输出 |
| 渲染丢帧、交互卡顿 | 相同内容与操作的时间数据；实际渲染/硬件路径、复制和转换、宿主调度；每次只改一项 |
| 缓慢内存增长、句柄增长 | 固定重复操作与观察窗口；预热/缓存后的增长、托管与原生资源、释放返回值和调用顺序 |

这些是排查方向，不是预设根因。CefSharp、FFmpeg 等应按各自实际版本与使用方式核对，不能照搬 VLC 的参数或推断。

## 避免再次产生虚假的确定性

- “同底层引擎的官方应用正常”提示需要比较集成方式，不能自动证明 SDK 默认配置正常。
- “PCM 对比正确”必须说明采集位置和被绕过的路径。
- “测试通过”必须说明测试的是调用成功、实际模块、资源释放，还是用户可感知的质量。
- “调低音量后减轻”不能单独证明增益过大；它也会让已经存在的失真变小。
- “改默认参数后恢复”证明一个有效配置差异，不自动等同于已经解释全部内部机理。

把隐含选择变成可观察、可对比、可追溯的选择，是这次问题最应该保留的工程经验。
